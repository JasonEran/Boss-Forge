# HR 智能简历筛选 Dashboard 产品需求文档（PRD）

> 文档版本：V0.3（评审稿）
>
> 编写日期：2026-08-31
>
> 使用范围：公司内网
>
> 底层候选人操作能力：[joohw/boss-cli](https://github.com/joohw/boss-cli)

## 1. 项目背景

HR 当前需要在 Boss 直聘中重复执行岗位选择、条件设置、候选人查找、简历判断和打招呼等操作。项目计划基于 `boss-cli` 建设一个仅在公司内网使用的 HR Dashboard，把候选人搜索、规则筛选、人工审核和打招呼串成可配置、可追踪的工作流。

系统分两个阶段上线：

- 第一阶段：系统筛选并列出符合条件的候选人，由 HR 人工审核，确认后手动点击“打招呼”。重点验证候选人数据和规则命中的准确性。
- 第二阶段：第一阶段数据验证通过后，增加“自动打招呼”能力。自动化必须由开关控制，默认关闭，并提供限额、审计和紧急停止能力。

## 2. 产品目标

### 2.1 核心目标

1. HR 可在 Dashboard 中为不同岗位维护筛选条件，无需编辑脚本。
2. 支持“立即执行”和“按设定时间执行”两种运行方式。
3. 自动采集并初筛候选人，清晰展示命中和不命中原因。
4. 第一阶段确保每次打招呼都由 HR 明确触发。
5. 第二阶段在受控条件下自动打招呼，并可随时关闭。
6. 全流程留痕，可追溯任务、规则版本、候选人状态和操作人员。

### 2.2 成功指标

第一阶段建议连续试运行 2～4 周，并按岗位统计：

| 指标 | 定义 | 建议验收目标 |
|---|---|---|
| 数据完整率 | 关键字段成功获取的候选人数 / 候选人总数 | ≥ 95% |
| 筛选准确率 | HR 认为符合要求的人数 / 系统判定符合的人数 | ≥ 85% |
| 表达归一化准确率 | 标准能力标签识别正确的样本数 / 已识别样本数 | 试点词典 ≥ 95% |
| 关键硬条件漏判率 | 实际满足硬条件但系统未识别的样本数 / 实际满足样本数 | 试点词典 ≤ 5% |
| 可解释率 | 能展示明确命中/淘汰原因的记录占比 | 100% |
| 重复候选人率 | 同一岗位重复进入待审核列表的比例 | ≤ 2% |
| 任务成功率 | 无人工技术介入完成的任务数 / 总任务数 | ≥ 95% |
| 误打招呼数 | 未经人工确认或不满足规则却发送招呼的数量 | 第一期必须为 0 |

第二阶段开启自动打招呼前，需由业务负责人确认第一阶段指标达标。

## 3. 用户角色与权限

| 角色 | 主要权限 |
|---|---|
| HR 操作员 | 查看岗位和候选人；创建、运行任务；审核候选人；手动打招呼 |
| HR 管理员 | HR 操作员全部权限；管理规则模板、消息模板、自动打招呼开关和限额 |
| 系统管理员 | 账号、权限、运行节点、Boss 登录态、系统参数和故障处理 |
| 审计/只读人员 | 查看任务、候选人、规则版本和操作日志，不可执行动作 |

权限原则：最小权限、账号操作留痕、自动打招呼只允许 HR 管理员开启。

## 4. 产品范围

### 4.1 第一阶段范围

- 内网账号登录和角色权限。
- Boss 账号/运行节点状态展示。
- 岗位同步与岗位配置。
- 筛选规则创建、编辑、复制、启停和版本管理。
- 立即执行任务。
- 自定义时间执行任务。
- 候选人采集、字段标准化、规则筛选、去重和排序。
- 待审核候选人列表及候选人详情。
- HR 人工确认后，单个或批量手动点击打招呼。
- 招呼模板管理和发送前预览。
- 任务日志、操作日志、失败原因和导出。
- 每日额度、频率限制和异常暂停。

### 4.2 第二阶段范围

- 岗位级“自动打招呼”开关，默认关闭。
- 自动发送策略：时间段、每日上限、单任务上限、间隔、消息模板。
- 自动发送前的二次规则校验。
- 自动发送记录、失败重试和异常熔断。
- 全局紧急停止开关。

### 4.3 暂不纳入首期

- 自动与候选人持续对话或自动面试。
- 自动淘汰已经进入正式招聘流程的候选人。
- 跨招聘平台聚合。
- 使用候选人的敏感个人信息做歧视性筛选。
- 未经 HR 审核自动修改 Boss 侧职位或 JD。
- 对外网开放或提供多租户 SaaS 服务。

## 5. 总体业务流程

```text
岗位与规则配置
      ↓
选择执行方式：立即执行 / 定时执行
      ↓
调用 boss-cli 获取候选人及可用简历信息
      ↓
字段标准化 → 去重 → 硬性条件校验 → 综合评分
      ↓
符合条件候选人进入“待审核”列表
      ↓
第一阶段：HR 审核 → 人工点击打招呼
第二阶段：自动开关已开启且通过安全校验 → 自动打招呼
      ↓
结果、原因、消息和操作日志归档
```

## 6. 运行方式

### 6.1 立即执行

HR 选择岗位和规则版本，点击“立即执行”。系统创建一次性任务并进入队列，展示以下状态：

`等待中 → 运行中 → 待审核/已完成/部分成功/失败/已取消`

要求：

- 防止重复点击导致重复任务。
- 运行前展示预计使用的岗位、规则、搜索来源和招呼模式。
- 允许取消尚未开始的任务；运行中取消需安全停止，不继续发送消息。

### 6.2 自定义时间执行

HR 设定岗位、规则和执行时间，系统按计划创建任务。

首期支持：

- 指定日期时间执行一次。
- 按工作日/每周指定日期和时间重复执行。
- 时区默认为系统部署时区，并在界面明确展示。
- 支持启用、暂停、修改、删除计划；修改只影响未来任务。
- 同一 Boss 账号同一时间只运行一个涉及页面操作的任务，其他任务排队。

## 7. 筛选规则

### 7.1 规则结构

每个岗位可保存多个规则方案，但同一任务只能绑定一个确定的规则版本。规则分为：

- 硬性条件：任一条件不满足即淘汰。
- 加分条件：满足后增加综合评分。
- 排除条件：命中即淘汰。
- 排序条件：决定候选人在待审核列表中的优先级。

### 7.2 建议支持的条件

| 分类 | 条件示例 | 运算方式 |
|---|---|---|
| 基础条件 | 工作城市、期望城市、求职状态 | 等于、包含、任一匹配 |
| 工作经验 | 总工作年限、相关岗位年限 | 大于等于、区间 |
| 教育背景 | 学历、专业、毕业院校 | 等于、包含、排除 |
| 职业经历 | 当前/历史职位、行业、公司关键词 | 包含、任一匹配、排除 |
| 技能关键词 | Java、React、销售渠道等 | 全部满足、任一满足、关键词组 |
| 项目经验 | 项目关键词、目标场景 | 包含、语义匹配（后续可选） |
| 薪资与意向 | 期望薪资、岗位意向 | 区间、重叠判断 |
| 活跃信息 | 最近活跃时间 | 时间范围 |
| 自定义规则 | HR 输入的补充要求和加分项 | 关键词/人工可解释评分 |

### 7.3 多表达适配与能力归一化

简历中的同一项能力可能存在中文、英文、缩写、别名、数字格式和口语化表达差异。规则引擎必须先将简历原文归一化为标准能力标签，再进行条件判断，不能只依赖单个关键词的精确匹配。

示例：HR 配置硬性条件“英语专业八级”时，以下表达应归一化为标准标签 `TEM-8（英语专业八级）`：

- 英语专业八级
- 英语专八 / 专八
- TEM-8 / TEM8 / TEM 8
- Test for English Majors Band 8

但以下内容不得直接判定为满足：

- CET-6、大学英语六级、雅思 8 分（属于不同证书或能力体系）。
- “备考专八”“计划参加 TEM-8”“专八未通过”（未证明已经取得）。
- “英语八级水平”“接近专八”（只描述主观水平，未明确持证）。
- 仅出现“英语专业”，但没有八级证书或通过信息。

标准化处理流程：

```text
简历原文
  ↓
文本清洗（大小写、全半角、空格、连字符、中文数字）
  ↓
同义词/别名词典匹配
  ↓
上下文校验（已通过/持证/成绩、备考/未通过/否定）
  ↓
标准能力标签 + 置信度 + 原文证据
  ↓
规则判断：满足 / 不满足 / 信息不足 / 有歧义待复核
```

实现要求：

- 建立可维护的“标准能力词典”，每个标准项包含标准名称、类别、别名、正向表达、否定表达、易混淆项和版本号。
- 第一版至少覆盖试点岗位涉及的证书、技能、职位、学校/专业、行业和常见工具名称。
- 同义词匹配应忽略不影响语义的大小写、空格、全半角和连字符，例如 `TEM-8`、`TEM 8`、`tem8`。
- 必须进行上下文否定和状态识别，区分“已取得”“备考中”“未通过”“仅了解”。
- 对证书等级、技能版本和年限等带层级的信息进行结构化解析，不得将相近但不等价的概念互相替代。
- 每次命中需保存简历原文片段、标准化结果、词典版本和置信度，供 HR 查看和纠错。
- 高置信度且无冲突时可自动判定；低置信度、表达冲突或仅靠语义推断时进入“有歧义待复核”，第一阶段不得自动淘汰或自动打招呼。
- HR 可在审核台将误判标记为“别名遗漏”“否定识别错误”“概念混淆”等，管理员审核后更新词典；词典更新必须生成新版本。
- 历史任务保留原词典版本和原判定，不静默改写；可由 HR 主动发起规则回放查看新旧差异。
- 若后续使用大模型辅助识别，大模型只负责提取候选标准项和证据，最终结论仍由确定性规则校验；模型输出无证据时不得判定为满足。

### 7.4 规则执行要求

- 空值不得默认判定为满足；应标记为“信息不足”，由规则决定进入人工复核或淘汰。
- 每位候选人必须展示命中条件、未命中条件、缺失字段、综合评分和最终结论。
- 每个标准化条件必须展示“简历原文 → 标准标签 → 判定结果”，HR 可快速核对系统是否理解正确。
- 规则修改后生成新版本，历史任务继续引用执行时的旧版本。
- 支持用历史候选人进行“仅测试不发送”的规则回放。
- 不允许将民族、宗教、婚育状况、残障等敏感属性作为自动筛选或排序依据。

试点词典中每个硬性条件上线前应建立正例、反例、否定例、歧义例测试集。例如“英语专业八级”至少验证 `TEM8`、`TEM-8`、`专八`、`CET-6`、`雅思 8 分`、`备考专八`、`专八未通过` 和 `英语八级水平` 等表达，新增别名或修改判定逻辑后自动回归。

## 8. Dashboard 页面需求

### 8.1 首页总览

展示：

- 今日/本周运行任务数、获取候选人数、待审核人数、已通过和已淘汰人数。
- 手动/自动打招呼数量、成功率和剩余额度。
- 任务异常、登录态失效、限流和熔断告警。
- 各岗位漏斗：已获取 → 规则通过 → 人工通过 → 已打招呼。
- 最近任务及快捷“立即执行”入口。

### 8.2 岗位与规则页

- 展示从 Boss 侧获取的岗位列表。
- 配置岗位启用状态、负责人、规则方案和默认招呼模板。
- 规则支持可视化条件组：`且（AND）`、`或（OR）`、排除（NOT）。
- HR 配置标准能力时，界面展示已覆盖的常见写法、易混淆项和判定口径。例如选择“英语专业八级”后，展示已包含 `TEM-8/TEM8/专八`，但不包含 `CET-6/雅思 8 分`。
- 显示预计匹配范围；保存前进行规则冲突和空条件校验。
- 提供规则预览和历史版本对比。

### 8.3 标准能力词典页

- 按证书、技能、职位、行业、学校/专业和工具分类查看标准项。
- 管理标准名称、别名、正向表达、否定表达、易混淆项和适用岗位。
- 新增或修改词典项需要管理员审核，并生成不可变版本。
- 提供测试框：输入一段简历原文，实时展示标准化标签、置信度、证据和判定状态。
- 展示来自 HR 审核台的误判反馈及其修正状态。

### 8.4 任务中心

- 新建立即任务或定时计划。
- 按岗位、执行方式、创建人、状态和时间筛选。
- 查看开始/结束时间、候选人数、成功/失败数和失败原因。
- 支持安全重试：只处理未完成项，不重复写入或重复打招呼。
- 支持任务暂停、恢复、取消（受任务状态限制）。

### 8.5 候选人审核台

列表默认字段：

- 姓名或 Boss 侧可识别名称。
- 当前职位、工作年限、学历、所在城市、期望岗位/城市、期望薪资。
- 来源岗位、任务、获取时间。
- 规则得分、匹配结论和主要命中原因。
- 标准化证据，例如“简历原文：TEM8 → 标准标签：英语专业八级 → 结论：满足”。
- 审核状态、招呼状态、最后操作人和时间。

操作：

- 查看候选人详情及可用简历信息。
- 标记“通过”“不通过”“待补充信息”。
- 填写审核备注和不通过原因。
- 对标准化结果标记正确或误判，并选择误判类型。
- 单个或批量加入待打招呼队列。
- 发送前预览最终消息；第一阶段必须人工点击最终确认。
- 支持按条件筛选、排序和导出脱敏数据。

为避免误操作，批量打招呼需要二次确认，并展示目标人数、岗位、模板和预计发送量。

### 8.6 招呼设置页

- 按岗位维护多个消息模板。
- 支持受控变量，例如候选人称呼、岗位名称和 HR 名称。
- 变量缺失时使用安全兜底文案，禁止发送未替换占位符。
- 第二阶段提供自动开关、发送时段、每日上限、任务上限、最小发送间隔和失败熔断阈值。
- 页面顶部常驻全局紧急停止按钮。

### 8.7 系统与审计页

- Boss 登录态、Chrome/CDP 运行节点和 `boss-cli` 版本。
- 每次命令调用的开始时间、结束时间、退出结果和脱敏错误信息。
- 用户登录、规则修改、开关修改、任务创建、审核和发送操作日志。
- 审计日志仅追加，不允许普通用户修改或删除。

## 9. 候选人状态设计

候选人在同一岗位下建议使用以下状态：

| 状态 | 说明 |
|---|---|
| 已获取 | 已从 Boss 侧获取，等待解析 |
| 信息不足 | 关键字段缺失，需要人工判断 |
| 规则不通过 | 命中排除条件或未满足硬性条件 |
| 待审核 | 系统判断符合条件，等待 HR 审核 |
| 审核通过 | HR 确认可以联系 |
| 审核不通过 | HR 明确拒绝，需记录原因 |
| 待打招呼 | 已审核通过并进入发送队列 |
| 已打招呼 | 发送成功 |
| 发送失败 | 发送失败，可按策略重试 |
| 已跳过 | 已联系、重复候选人、额度不足或其他安全原因 |

同一候选人在不同岗位可有不同审核状态，但应提示跨岗位重复联系风险。

## 10. `boss-cli` 集成设计

### 10.1 复用原则

`boss-cli` 作为唯一的 Boss 页面操作层。凡是它已经提供的登录、Chrome/CDP 会话、页面导航、候选人读取、简历预览、OCR、聊天和候选人操作，Boss-Forge 一律通过 CLI 直接调用，不再用 Puppeteer、Playwright、Selenium 或私有接口重复实现。

Boss-Forge 只建设 `boss-cli` 不负责的招聘业务能力：Dashboard、权限、岗位规则、同义表达归一化、任务调度、人工审核、结果存储、幂等、安全策略和审计。

### 10.2 直接调用的现有能力

| Dashboard 场景 | 直接调用 | 已有能力与边界 | Boss-Forge 是否重写 |
|---|---|---|---|
| 登录与浏览器会话 | `boss login` | 复用本机 Chrome、CDP 和本地登录态；扫码/验证人工完成 | 否 |
| 岗位同步 | `boss positions` | 读取开放、待开放、已关闭职位及列表信息 | 否 |
| JD 同步 | `boss jd <岗位名称>` | 读取职位详情并输出/缓存 Markdown | 否 |
| 推荐候选人 | `boss recommend [岗位关键字]` | 切换岗位并读取推荐列表 | 否 |
| 常规搜索 | `boss search [关键词]` | 填写关键词并读取常规搜索结果 | 否 |
| 深度搜索条件 | `boss deep-search --core ... --bonus ...` | 同步 Boss 深度搜索的核心要求和加分项 | 否 |
| 执行深度匹配 | `boss deep-search ... --match` | 消耗平台匹配次数并返回最新 20 条 | 否 |
| 在线简历预览 | `boss preview <姓名>` | 在推荐、深度搜索或常规搜索当前列表中打开简历并保存截图 | 否 |
| 简历 OCR | `boss preview` 截图 + 配置的 OCR 提供方 | 支持 `boss-cli` 内置百度 OCR，或将截图提交腾讯云 `GeneralBasicOCR`；需服务端密钥 | 原则上否，隐私未批准时关闭 |
| 聊天候选人列表 | `boss list [--unread]` | 读取全部/未读会话、岗位、时间、消息摘要 | 否 |
| 打开候选人聊天 | `boss chat <姓名>` 或 `boss chat --index <序号>` | 支持模糊/精确匹配；同名可按列表序号打开 | 否 |
| 发送文本消息 | `boss send --text <内容>` | 在当前候选人会话发送文本 | 否 |
| 发送并索取简历 | `boss send --text <内容> --request-resume` | 发消息后执行求附件简历 | 否 |
| 推荐/深搜打招呼 | `boss greet <姓名> --job <岗位>` | 在当前推荐或深度搜索列表打招呼 | 否 |
| 在线简历截图/OCR | `boss action resume` | 在已打开聊天中读取在线简历，截图并可 OCR | 否 |
| 标记不合适 | `boss action not-fit` | 在当前聊天中执行“不合适” | 否 |
| 候选人备注 | `boss action remark --remark <内容>` | 更新 Boss 侧候选人备注 | 否 |
| 接受附件简历 | `boss action agree-resume` | 处理对方发送附件简历的确认卡片 | 否 |
| 主动求附件简历 | `boss action request-attachment-resume` | 发送 Boss 默认求简历话术；需满足平台前置条件 | 否 |
| 沟通记录 | `boss action history` | 读取同事沟通和我的沟通记录 | 否 |
| 交换微信 | `boss action wechat` | 点击换微信并确认 | 否 |

以上调用以锁定版本的 `boss help` 和源码行为为准。Dashboard 按能力调用，不复制选择器、页面 URL、随机操作延时、弹窗处理、会话锁或简历截图逻辑。

### 10.3 Boss-Forge 必须补齐的能力

| 能力 | 为什么不能直接由 `boss-cli` 提供 |
|---|---|
| Web Dashboard | `boss-cli` 是纯命令行，不提供多用户业务界面 |
| 用户、角色和权限 | CLI 复用本机登录态，不管理公司内部用户权限 |
| 立即/定时任务调度 | CLI 执行单条命令，不维护业务计划、队列和任务状态 |
| 规则版本与标准能力词典 | CLI 可把自然语言条件传给 Boss，但不负责 `TEM8/专八` 等标准化和确定性校验 |
| 候选人结构化档案 | CLI 主要输出纯文本和本地截图/OCR，不提供招聘数据库 |
| 跨任务与跨岗位去重 | CLI 不维护公司的长期候选人联系历史和冷却期 |
| 人工审核工作流 | CLI 不提供待审核、通过、拒绝、备注和复核队列 |
| 自动打招呼业务开关 | CLI 提供一次 `greet` 操作，不提供全局/岗位/任务三级策略 |
| 幂等与发送安全 | CLI 执行命令，系统需防止重复任务、重复消息和不确定结果重发 |
| 审计和业务报表 | CLI 返回执行结果，但不提供公司级不可变审计、漏斗和指标 |

### 10.4 明确不重复建设

- 不自行开发 Boss 页面爬虫、DOM 选择器和页面导航。
- 不自行启动或控制第二套 Chrome/CDP 会话。
- 不自行实现推荐、常规搜索、深度搜索、岗位和 JD 抓取。
- 不自行实现简历弹层打开和长截图；始终复用 `boss-cli`。OCR 使用经过批准的提供方适配器。
- 不自行实现聊天打开、消息发送、打招呼、备注、不合适、求简历、沟通记录或换微信。
- 不把 `boss-cli` 源码复制进 Boss-Forge；优先安装锁定版本的 npm 包并以子进程调用。
- 只有当关键能力在锁定版本中不存在、已向上游确认不支持，且业务明确批准后，才单独评审是否扩展；优先向 `boss-cli` 上游贡献能力。

### 10.5 适配层要求

- Dashboard 后端通过服务端适配层调用 CLI，浏览器不得直接执行命令。
- 使用参数数组调用子进程，不经过 Shell 拼接；只开放命令白名单并校验参数类型、长度和枚举。
- 适配层只负责进程超时、退出码、输出解析、任务关联和脱敏日志；不包含 Boss 页面选择器或页面操作逻辑。
- 同一 Boss 账号的 CLI 调用必须串行，尊重 `boss-cli` 自身会话锁，不另建并行浏览器会话。
- 同名候选人优先使用 `boss chat --index` 及岗位/当前列表上下文，不能只依赖姓名。
- `deep-search --match` 会消耗匹配次数且只返回最新 20 条，任务应记录批次并避免重复调用。
- `preview` 受平台每日预览次数或访问频率限制，优先复用已完成的精筛结果；达到限制时标记“信息不足”并停止当日继续预览。公开资料无法确认其属于付费额度。
- 腾讯云模式保持 `BOSS_RESUME_OCR=0`，由 Worker 将 `boss-cli` 生成的截图提交 `GeneralBasicOCR`；密钥仅从服务端环境变量读取。未获隐私与安全批准时关闭 `BOSS_FORGE_RESUME_PREVIEW_ENABLED`。
- 登录失效、验证码、人机校验或页面结构变化时立即暂停并通知管理员，不由 Boss-Forge 绕过。
- 生产固定验证过的 npm 版本，不调用 `boss update` 自动升级；升级前回归输出解析和关键流程。
- 若修改或分发 `boss-cli`，需在实施前完成 GPL-3.0 许可证义务评估；首选不改源码、通过已安装 CLI 调用。

## 11. 自动打招呼安全机制（第二阶段）

自动发送必须同时满足以下条件：

1. 全局自动化总开关已开启。
2. 对应岗位自动打招呼开关已开启。
3. 当前任务明确允许自动发送。
4. 候选人满足已锁定的规则版本，且二次校验通过。
5. 候选人未被同一岗位联系，且未命中跨岗位联系冷却期。
6. 当前时间位于允许发送时段。
7. 未超过账号、岗位、任务的每日/单次上限。
8. 登录态和运行环境正常，未触发异常熔断。

建议默认安全参数：

- 自动开关默认关闭，部署、升级和异常恢复后不自动开启。
- 每次发送保留随机化的合理间隔，但不得以规避平台风控为目的。
- 连续失败达到阈值后自动暂停，等待管理员处理。
- 任何人关闭全局开关后，尚未发送的队列立即停止。
- 开关变更、批量发送和紧急停止均写入审计日志。

## 12. 数据设计（核心对象）

| 对象 | 关键字段 |
|---|---|
| 用户 | 用户 ID、姓名、角色、状态、最后登录时间 |
| Boss 账号 | 账号 ID、所属主体、登录状态、运行节点、最后校验时间 |
| 岗位 | 岗位 ID、Boss 岗位标识、名称、状态、负责人 |
| 规则方案 | 规则 ID、岗位 ID、版本、条件 JSON、状态、创建人 |
| 标准能力词典 | 标准项 ID、类别、标准名称、别名、否定表达、易混淆项、版本 |
| 识别证据 | 候选人、标准项、简历原文片段、归一化结果、置信度、词典版本、人工纠错 |
| 执行计划 | 计划 ID、岗位、规则版本、执行时间/周期、启停状态 |
| 任务 | 任务 ID、来源计划、执行方式、状态、起止时间、统计数据 |
| 候选人 | 内部 ID、平台临时标识、标准化字段、原始数据引用 |
| 岗位候选关系 | 岗位、候选人、任务、规则结论、评分、审核状态 |
| 招呼记录 | 候选人、岗位、模板版本、发送模式、结果、发送人/系统 |
| 审计日志 | 操作者、动作、对象、前后值摘要、时间、请求 ID |

数据保存期限、删除流程和备份周期需在上线前由公司隐私/法务与 HR 共同确定。候选人数据仅用于招聘目的，界面和导出应按角色脱敏。

## 13. 非功能需求

### 13.1 安全

- 仅内网访问，接入公司统一身份认证或独立账号加双因素认证。
- Cookie、浏览器用户目录、候选人数据和消息内容加密存储。
- 密钥与配置分离，不进入代码仓库和前端包。
- 后端命令白名单；所有用户输入进行类型、长度和字符校验。
- 导出文件加水印、操作人标记和有效期控制（如公司条件允许）。

### 13.2 可靠性

- 任务和发送操作具备幂等键，重复请求不得重复打招呼。
- 服务重启后可恢复未完成任务，但发送前必须重新校验状态。
- 单个候选人失败不应导致整个任务丢失已完成结果。
- 核心任务、登录失效、连续失败和额度耗尽需要告警。

### 13.3 性能

- Dashboard 常规页面在内网环境下 3 秒内展示首屏数据。
- 创建任务后 2 秒内反馈任务编号和排队状态。
- 候选人列表支持至少 10,000 条岗位候选关系的分页、筛选和排序。
- 页面自动化吞吐以平台允许范围和安全限额为上限，不以高并发为目标。

### 13.4 可维护性

- `boss-cli` 通过独立适配层接入，避免业务逻辑依赖其文本格式。
- 规则引擎、任务调度、审核和发送模块解耦。
- 记录应用版本、CLI 版本和规则版本，便于复现历史结果。

## 14. 异常处理

| 异常 | 系统行为 |
|---|---|
| Boss 登录态失效 | 暂停相关任务，通知管理员人工重新登录 |
| 出现验证码/人机验证 | 立即暂停自动操作，不尝试绕过 |
| CLI 超时或崩溃 | 记录上下文，有限次数重试；连续失败后熔断 |
| 页面结构变化/输出解析失败 | 标记任务部分成功或失败，保留原始脱敏输出 |
| 简历每日预览次数或频率受限 | 停止预览，候选人标记为信息不足 |
| 匹配/发送额度不足 | 队列暂停至额度恢复或由 HR 调整任务 |
| 重复候选人 | 合并展示历史记录，默认跳过重复联系 |
| 规则在任务执行中被修改 | 当前任务继续使用已锁定版本，新任务使用新版本 |
| 消息发送结果不确定 | 标记“待核验”，查询/人工确认前禁止重发 |

## 15. 合规与使用边界

- 上线前确认公司使用方式符合 Boss 直聘最新用户协议、平台规则及适用的个人信息保护要求。
- 不绕过验证码、人机验证、访问控制、平台限额或其他技术保护措施。
- 不采集与招聘目的无关的信息，不使用敏感属性实施歧视性筛选。
- 候选人数据只在授权人员和内网系统中使用，不上传至未经批准的第三方服务。
- 若后续引入大模型做语义匹配，需先确认模型部署位置、数据出境、日志保留和供应商数据使用政策。
- 保留人工申诉、纠错和删除机制；自动评分仅作为辅助，不作为不可复核的最终决定。

## 16. 分阶段验收标准

### 16.1 第一阶段验收

- HR 能创建岗位规则并选择立即或定时运行。
- 系统能完成候选人获取、标准化、去重、规则筛选并列出待审核结果。
- 系统能将试点词典中的同义表达正确映射为标准能力，并能识别否定、备考和易混淆表达。
- 每个候选人均显示筛选结论及可解释原因。
- 每次能力命中均展示原文证据、标准标签、置信度和使用的词典版本；有歧义结果进入人工复核。
- HR 可完成人工通过/拒绝，并在明确确认后单个或批量打招呼。
- 未经人工确认不能发送任何招呼。
- 重跑任务不会重复创建相同岗位候选记录，也不会重复打招呼。
- 登录失效、验证码、额度不足和 CLI 异常均能安全暂停并提示。
- 可按任务、岗位和操作人查询完整审计日志。
- 试运行数据达到第 2.2 节指标或由业务负责人书面接受偏差。

### 16.2 第二阶段验收

- 自动打招呼默认关闭，仅管理员可开启。
- 全局、岗位、任务三级控制均生效，任一关闭均不得自动发送。
- 每次自动发送均能追溯候选人、规则版本、模板版本和触发任务。
- 每日限额、发送时段、冷却期、失败熔断和紧急停止有效。
- 服务重启、重复回调或不确定结果不会导致重复打招呼。
- 自动化异常时系统优先停止发送，并保留待处理队列。

## 17. 推荐实施架构

```text
内网浏览器
   ↓
HR Dashboard（前端）
   ↓
业务 API / 权限 / 审计
   ├── 岗位与规则服务
   ├── 候选人审核服务
   ├── 任务调度与队列
   └── 招呼策略与安全控制
             ↓
       boss-cli 适配层
             ↓
   本机 Chrome / CDP / Boss 直聘

数据库：岗位、规则、任务、候选人、审核、发送与审计记录
```

建议将调用 Chrome/CDP 的 Worker 部署在独立受控节点。业务 API 只投递任务，Worker 串行执行同一 Boss 账号的页面操作，减少会话冲突。

## 18. 建议里程碑

| 里程碑 | 交付内容 |
|---|---|
| M0 技术验证 | 跑通登录、岗位获取、候选人获取、结果解析和一次人工打招呼 |
| M1 数据闭环 | 岗位/规则、立即任务、候选人标准化、去重、待审核列表 |
| M2 一期可用 | 定时任务、人工审核、手动打招呼、日志、限额和异常处理 |
| M3 试运行 | 2～4 周准确性验证、规则调整、问题修复和指标复盘 |
| M4 二期上线 | 自动开关、自动发送策略、熔断、紧急停止和完整审计 |

## 19. 待业务确认事项

1. 首批试点岗位及每个岗位预计每日候选人量。
2. “自定义时间执行”是否需要一次性、工作日、每周之外的复杂周期。
3. 第一阶段是允许批量人工确认发送，还是必须逐个候选人确认。
4. 候选人硬性条件、加分条件和排除条件的首版模板。
5. 多岗位重复候选人的联系规则及冷却周期。
6. 招呼消息模板、变量和审批人。
7. 第一阶段转第二阶段的最终指标阈值和审批人。
8. 候选人数据保存期限、导出权限、删除和备份要求。
9. 是否一个 Dashboard 管理多个 Boss 账号；若是，需要明确账号与岗位的归属关系。
10. 内网身份认证方式、告警渠道和系统管理员名单。

## 20. 技术调研结论

`boss-cli` 适合作为早期技术验证和页面操作适配层：它基于 Puppeteer/CDP 复用本机 Chrome 登录态，提供岗位、推荐/搜索、深度搜索、简历预览和打招呼等能力，并以文本形式输出结果。但它不是完整的招聘业务后端，Dashboard 仍需自行建设结构化数据模型、任务调度、规则引擎、权限、审计、幂等和安全控制。

正式开发前建议锁定一个经过验证的 `boss-cli` 版本，并完成一次技术 Spike，重点验证：候选人唯一标识、输出稳定性、深度搜索批次、预览额度、发送结果确认、登录态恢复和页面变更时的失败行为。
