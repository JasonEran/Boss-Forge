# HR 智能简历筛选 Dashboard 产品需求文档（PRD）

> 版本：V0.2（评审稿）  
> 日期：2026-08-31  
> 范围：公司内网  
> 底层能力：[joohw/boss-cli](https://github.com/joohw/boss-cli)

## 1. 项目背景

项目计划基于 `boss-cli` 建设仅在公司内网使用的 HR Dashboard，把岗位选择、候选人搜索、简历筛选、人工审核和打招呼串成可配置、可追踪的工作流。

- 第一阶段：系统筛选并列出符合条件的候选人，由 HR 核验数据并人工点击“打招呼”。
- 第二阶段：第一阶段验证通过后，增加可控的自动打招呼能力。自动化默认关闭，并提供限额、审计、熔断和紧急停止。

## 2. 产品目标与指标

### 2.1 核心目标

1. HR 可为不同岗位维护筛选条件，无需编辑脚本。
2. 支持“立即执行”和“按设定时间执行”。
3. 自动采集、标准化、去重和初筛候选人，并解释判断依据。
4. 第一期所有打招呼操作必须由 HR 明确确认。
5. 第二期自动发送必须受全局、岗位、任务三级开关控制。
6. 全流程可追溯任务、规则、词典、候选人、消息和操作人员。

### 2.2 建议成功指标

| 指标 | 定义 | 建议目标 |
|---|---|---|
| 数据完整率 | 关键字段成功获取人数 / 候选人总数 | ≥ 95% |
| 筛选准确率 | HR 认为符合人数 / 系统判定符合人数 | ≥ 85% |
| 表达归一化准确率 | 标准能力标签识别正确数 / 已识别数 | 试点词典 ≥ 95% |
| 关键硬条件漏判率 | 实际满足但系统未识别数 / 实际满足数 | 试点词典 ≤ 5% |
| 可解释率 | 有明确命中、淘汰及证据的记录占比 | 100% |
| 重复候选人率 | 同岗位重复进入待审核列表的比例 | ≤ 2% |
| 任务成功率 | 无技术人员介入完成任务数 / 总任务数 | ≥ 95% |
| 误打招呼数 | 未经授权或不满足条件却发送的数量 | 第一期必须为 0 |

第一阶段建议按岗位连续试运行 2～4 周。第二阶段开启前，由业务负责人确认指标达标或书面接受偏差。

## 3. 用户与权限

| 角色 | 权限 |
|---|---|
| HR 操作员 | 查看岗位和候选人、创建任务、审核、人工打招呼 |
| HR 管理员 | 操作员全部权限；管理规则、词典、模板、限额及自动开关 |
| 系统管理员 | 账号、权限、运行节点、Boss 登录态、配置和故障处理 |
| 审计人员 | 只读查看任务、规则版本、消息及操作日志 |

采用最小权限原则；自动打招呼只允许 HR 管理员开启，所有关键操作留痕。

## 4. 产品范围

### 4.1 第一阶段

- 内网登录和角色权限。
- Boss 账号、登录态及运行节点状态。
- 岗位同步、岗位配置、规则与标准能力词典。
- 立即任务和自定义时间任务。
- 候选人采集、字段标准化、同义表达归一化、去重、筛选和排序。
- 待审核列表、候选人详情及判断证据。
- HR 人工审核，单个或批量确认后手动打招呼。
- 招呼模板、发送预览、额度与频率限制。
- 任务、错误、审核、消息和审计日志。

### 4.2 第二阶段

- 岗位级自动打招呼开关，默认关闭。
- 发送时段、每日上限、单任务上限、间隔与模板。
- 发送前二次校验、失败重试、异常熔断和全局紧急停止。

### 4.3 暂不纳入首期

- 自动持续对话、自动面试或自动修改职位/JD。
- 跨招聘平台聚合、多租户 SaaS 或外网开放。
- 使用敏感个人属性进行歧视性筛选。
- 未经批准把候选人数据上传至第三方模型或服务。

## 5. 业务流程

```text
岗位与规则配置
  → 立即执行 / 定时执行
  → boss-cli 获取候选人和可用简历信息
  → 字段标准化与同义表达归一化
  → 去重、硬条件校验、综合评分
  → 符合条件候选人进入待审核
  → 第一期：HR 审核并人工点击打招呼
  → 第二期：自动开关开启且通过安全校验后自动打招呼
  → 全流程结果与日志归档
```

## 6. 运行方式

### 6.1 立即执行

HR 选择岗位和规则版本后点击“立即执行”，系统创建一次性任务：

`等待中 → 运行中 → 待审核 / 已完成 / 部分成功 / 失败 / 已取消`

- 防止重复点击产生重复任务。
- 运行前展示岗位、规则、数据来源和打招呼模式。
- 等待中的任务可取消；运行中的任务安全停止，不继续发送消息。

### 6.2 自定义时间执行

- 指定日期时间执行一次。
- 按工作日或每周指定日期和时间重复执行。
- 明确展示部署时区。
- 计划可启用、暂停、修改和删除，修改只影响未来任务。
- 同一 Boss 账号同一时间只运行一个页面操作任务，其他任务排队。

## 7. 筛选规则

### 7.1 规则结构

- 硬性条件：任一不满足即淘汰。
- 加分条件：满足后增加综合评分。
- 排除条件：命中即淘汰。
- 排序条件：决定待审核顺序。

每个岗位可保存多个规则方案，但任务必须锁定一个不可变的规则版本。

### 7.2 建议条件

| 分类 | 示例 | 运算方式 |
|---|---|---|
| 基础条件 | 工作城市、期望城市、求职状态 | 等于、包含、任一匹配 |
| 工作经验 | 总年限、相关岗位年限 | 大于等于、区间 |
| 教育背景 | 学历、专业、学校 | 等于、包含、排除 |
| 职业经历 | 职位、行业、公司关键词 | 包含、任一、排除 |
| 技能与证书 | Java、React、TEM-8 等 | 全部、任一、等级判断 |
| 项目经验 | 项目关键词、目标场景 | 包含、受控语义识别 |
| 薪资与意向 | 期望薪资、岗位意向 | 区间、重叠判断 |
| 活跃信息 | 最近活跃时间 | 时间范围 |

### 7.3 多表达适配与能力归一化

同一能力可能存在中文、英文、缩写、别名、数字格式和口语化差异。规则引擎必须先将简历原文归一化为标准能力标签，再进行判断，不能只依赖单一关键词。

例如 HR 配置硬条件“英语专业八级”时，以下表达归一化为 `TEM-8（英语专业八级）`：

- 英语专业八级
- 英语专八 / 专八
- TEM-8 / TEM8 / TEM 8
- Test for English Majors Band 8

以下表达不得直接判定为满足：

- CET-6、大学英语六级、雅思 8 分：不同证书或体系。
- “备考专八”“计划参加 TEM-8”“专八未通过”：未证明已经取得。
- “英语八级水平”“接近专八”：主观水平，不代表持证。
- 只有“英语专业”而没有八级证书或通过信息。

处理流程：

```text
简历原文
  → 文本清洗（大小写、全半角、空格、连字符、中文数字）
  → 同义词/别名词典匹配
  → 上下文校验（已通过/持证/成绩、备考/未通过/否定）
  → 标准标签 + 置信度 + 原文证据
  → 满足 / 不满足 / 信息不足 / 有歧义待复核
```

要求：

- 建立可维护的标准能力词典，包括标准名称、类别、别名、正向表达、否定表达、易混淆项和版本。
- 第一版覆盖试点岗位所需证书、技能、职位、学校/专业、行业和工具名称。
- 忽略无语义影响的大小写、空格、全半角和连字符差异。
- 识别“已取得、备考中、未通过、仅了解”等状态及上下文否定。
- 对证书等级、技能版本和年限结构化解析，不把相近但不等价的概念互换。
- 每次判断保存原文证据、标准化结果、置信度、词典版本。
- 低置信度、冲突或纯语义推断进入人工复核，第一期不得据此自动淘汰或打招呼。
- HR 可标记“别名遗漏、否定识别错误、概念混淆”等误判；管理员审核后更新词典并生成新版本。
- 历史任务保留原词典和判断版本，需要时主动回放查看新旧差异。
- 若使用大模型，大模型只提取候选标准项和证据，确定性规则负责最终校验；无原文证据不得判定满足。

每个硬条件上线前建立正例、反例、否定例和歧义例测试集。例如专八至少覆盖 `TEM8`、`TEM-8`、`专八`、`CET-6`、`雅思 8 分`、`备考专八`、`专八未通过`、`英语八级水平`，词典变更后自动回归。

### 7.4 通用执行要求

- 空值不默认满足，标记“信息不足”，根据规则进入复核或淘汰。
- 展示“简历原文 → 标准标签 → 判定结果”、缺失字段、分数和结论。
- 规则修改生成新版本，历史任务继续引用旧版本。
- 支持对历史候选人进行仅测试、不发送的规则回放。
- 不允许把民族、宗教、婚育、残障等敏感属性用于筛选或排序。

## 8. Dashboard 页面

### 8.1 首页

- 今日/本周任务、获取人数、待审核、通过、淘汰和已联系人数。
- 手动/自动打招呼数量、成功率、剩余额度。
- 登录失效、限流、熔断和任务异常告警。
- 岗位漏斗：已获取 → 规则通过 → 人工通过 → 已打招呼。
- 最近任务和“立即执行”入口。

### 8.2 岗位与规则

- 同步 Boss 岗位，配置负责人、启用状态、规则和默认模板。
- 可视化配置 `AND`、`OR`、`NOT` 条件组。
- 选择标准能力时展示常见写法、易混淆项及判定口径。
- 保存前检查空条件与冲突，支持预览和版本对比。

### 8.3 标准能力词典

- 按证书、技能、职位、行业、学校/专业和工具分类。
- 管理标准名、别名、正向/否定表达、易混淆项和适用岗位。
- 变更需管理员审核并生成不可变版本。
- 测试框实时展示标签、置信度、证据和判定状态。
- 展示 HR 反馈的误判及修正状态。

### 8.4 任务中心

- 新建立即任务和定时计划。
- 按岗位、方式、创建人、状态、时间筛选。
- 查看候选人数、成功/失败数及原因。
- 安全重试只处理未完成项，不重复写入或打招呼。
- 按任务状态支持暂停、恢复和取消。

### 8.5 候选人审核台

列表展示候选人的岗位、经验、学历、城市、薪资、来源任务、规则分数、命中原因、审核和联系状态。

- 查看可用简历信息及“原文 → 标准标签 → 结论”证据。
- 标记通过、不通过或待补充，并填写原因和备注。
- 纠正标准化误判，选择误判类型。
- 单个或批量加入待打招呼队列。
- 第一期发送前必须由 HR 预览并最终确认。
- 批量发送二次确认人数、岗位、模板和发送量。
- 可筛选、排序并按权限导出脱敏数据。

### 8.6 招呼设置

- 按岗位维护多个消息模板和受控变量。
- 变量缺失使用安全兜底，禁止发送未替换占位符。
- 第二期配置三级开关、时段、每日/任务上限、最小间隔和熔断阈值。
- 页面常驻全局紧急停止按钮。

### 8.7 系统与审计

- 展示 Boss 登录态、Chrome/CDP 节点和 `boss-cli` 版本。
- 记录命令起止时间、退出结果和脱敏错误。
- 记录登录、规则/词典/开关修改、任务、审核和发送操作。
- 审计日志仅追加，普通用户不可修改或删除。

## 9. 候选人状态

`已获取 → 信息不足 / 规则不通过 / 待审核 → 审核通过 / 审核不通过 → 待打招呼 → 已打招呼 / 发送失败 / 已跳过`

同一候选人在不同岗位可有不同审核状态，但应提示跨岗位重复联系风险。

## 10. boss-cli 集成

| 业务能力 | CLI 能力 |
|---|---|
| 登录 | `boss login`，扫码/验证人工完成 |
| 岗位/JD | `boss positions`、`boss jd <名称>` |
| 推荐与搜索 | `boss recommend`、`boss search` |
| 深度搜索 | `boss deep-search ... --match` |
| 简历预览 | `boss preview <姓名>` |
| 打招呼 | `boss greet <姓名> --job <岗位>` |

集成要求：

- 由服务端适配层调用 CLI，禁止浏览器直接执行。
- 命令白名单、参数校验、超时、重试、账号互斥锁和输出解析。
- 禁止把未经校验的输入拼入 Shell 命令。
- 保存脱敏原始输出和结构化结果。
- 同名候选人不能只依赖姓名，应组合岗位、列表上下文等标识。
- `deep-search --match` 会消耗次数且目前只输出最新 20 条，应记录批次并防止重复。
- `preview` 有每日额度，额度不足时标记信息不足，不伪造结论。
- 登录失效、验证码、人机校验或页面变化时立即暂停并告警。
- 生产固定验证过的 CLI 版本，升级前回归解析与关键流程。

## 11. 自动打招呼安全机制（第二阶段）

自动发送必须同时满足：

1. 全局开关开启。
2. 岗位开关开启。
3. 任务明确允许自动发送。
4. 候选人满足锁定规则且发送前二次校验通过。
5. 未重复联系，也未命中跨岗位冷却期。
6. 当前位于允许时段，且未超过账号、岗位、任务限额。
7. 登录态与运行环境正常，未触发熔断。

部署、升级和异常恢复后不得自动重开；连续失败达到阈值后暂停；关闭全局开关应立即停止未发送队列；所有开关和发送行为写入审计日志。

## 12. 核心数据对象

| 对象 | 关键字段 |
|---|---|
| 用户 | ID、姓名、角色、状态、最后登录 |
| Boss 账号 | ID、所属主体、登录状态、节点、最后校验 |
| 岗位 | ID、Boss 标识、名称、状态、负责人 |
| 规则 | ID、岗位、版本、条件 JSON、状态、创建人 |
| 标准能力词典 | 标准项、类别、别名、否定表达、易混淆项、版本 |
| 识别证据 | 候选人、标准项、原文、结果、置信度、词典版本、纠错 |
| 执行计划 | 岗位、规则版本、时间/周期、启停状态 |
| 任务 | 来源计划、方式、状态、起止时间、统计 |
| 候选人 | 内部 ID、平台临时标识、标准化字段、原始数据引用 |
| 岗位候选关系 | 岗位、候选人、任务、结论、评分、审核状态 |
| 招呼记录 | 候选人、岗位、模板版本、模式、结果、操作者 |
| 审计日志 | 操作者、动作、对象、前后值摘要、时间、请求 ID |

候选人数据保存期限、删除流程和备份周期须由隐私/法务与 HR 上线前确认；仅用于招聘并按角色脱敏。

## 13. 非功能要求

- 仅限内网，接入统一身份认证或账号加双因素认证。
- Cookie、浏览器用户目录、候选人数据和消息加密存储。
- 密钥与代码分离，不进入代码仓库或前端包。
- 任务和发送使用幂等键，重复请求不得重复联系。
- 服务重启可恢复任务，但发送前重新校验。
- 页面首屏目标 3 秒内展示；任务创建 2 秒内返回编号和排队状态。
- 候选人列表支持至少 10,000 条岗位候选关系的分页、筛选和排序。
- 规则、调度、审核、发送和 CLI 适配层解耦。

## 14. 异常处理

| 异常 | 行为 |
|---|---|
| 登录失效 | 暂停任务并通知人工登录 |
| 验证码/人机验证 | 立即暂停，不尝试绕过 |
| CLI 超时/崩溃 | 有限重试，连续失败熔断 |
| 输出解析失败 | 标记部分成功/失败，保留脱敏原始输出 |
| 简历额度耗尽 | 停止预览，标记信息不足 |
| 匹配/发送额度不足 | 暂停队列，等待恢复或人工调整 |
| 重复候选人 | 合并历史，默认跳过重复联系 |
| 执行中规则被修改 | 当前任务继续用锁定版本 |
| 发送结果不确定 | 标记待核验，确认前禁止重发 |

## 15. 合规边界

- 上线前确认使用方式符合 Boss 直聘最新协议、平台规则和个人信息保护要求。
- 不绕过验证码、访问控制、平台限额或技术保护措施。
- 不采集招聘无关信息，不使用敏感属性进行歧视性筛选。
- 候选人数据只在授权内网使用，不上传未经批准的第三方。
- 引入模型前确认部署、数据出境、日志保留和供应商数据政策。
- 保留人工纠错、申诉和删除机制；自动评分仅作辅助。

## 16. 分阶段验收

### 16.1 第一阶段

- 可配置岗位、版本化规则和立即/定时任务。
- 完成采集、标准化、去重、筛选并列出待审核结果。
- 试点同义表达正确归一化，能够识别否定、备考和易混淆项。
- 每项命中展示原文证据、标准标签、置信度和词典版本。
- 歧义结果进入人工复核。
- HR 可审核并在明确确认后单个或批量打招呼。
- 未经人工确认不能发送；重跑不重复建档或发送。
- 登录、验证码、额度和 CLI 异常均安全暂停并提示。
- 可按任务、岗位和人员查询完整审计日志。

### 16.2 第二阶段

- 自动开关默认关闭，仅管理员可开启。
- 全局、岗位、任务三级控制均生效。
- 自动发送可追溯候选人、规则、词典、模板和任务版本。
- 时段、限额、冷却期、熔断和紧急停止有效。
- 重启、重复请求或不确定结果不会造成重复联系。

## 17. 推荐架构

```text
内网浏览器
  → HR Dashboard
  → 业务 API / 权限 / 审计
     ├─ 岗位与规则服务
     ├─ 标准能力词典与识别服务
     ├─ 候选人审核服务
     ├─ 任务调度与队列
     └─ 招呼策略与安全控制
          → boss-cli 适配层
          → 本机 Chrome / CDP / Boss 直聘
```

Chrome/CDP Worker 建议部署在独立受控节点；API 只投递任务，Worker 串行执行同一 Boss 账号的页面操作。

## 18. 里程碑

| 阶段 | 交付 |
|---|---|
| M0 技术验证 | 登录、岗位/候选人获取、解析、唯一标识、一次人工打招呼 |
| M1 数据闭环 | 规则、词典、立即任务、标准化、去重和审核列表 |
| M2 一期可用 | 定时任务、人工审核/发送、日志、限额和异常处理 |
| M3 试运行 | 2～4 周准确率验证、词典/规则调整和指标复盘 |
| M4 二期上线 | 自动开关、发送策略、熔断、紧急停止和完整审计 |

## 19. 待确认事项

1. 首批试点岗位及每日候选人量。
2. 定时执行是否需要更复杂的周期。
3. 第一期允许批量人工确认，还是必须逐人确认。
4. 首版硬性、加分、排除条件和标准能力词典。
5. 跨岗位重复候选人的联系规则和冷却周期。
6. 招呼模板、变量和审批人。
7. 第一期转第二期的指标阈值和审批人。
8. 数据保存期限、导出、删除和备份要求。
9. 是否管理多个 Boss 账号及账号和岗位归属。
10. 内网认证方式、告警渠道和管理员名单。

## 20. 技术结论

`boss-cli` 适合作为早期技术验证和页面操作适配层，但不是完整招聘业务后端。Dashboard 仍需建设结构化数据、任务调度、规则与词典、审核、权限、审计、幂等及安全控制。

正式开发前应锁定经过验证的版本并完成技术 Spike，重点验证候选人唯一标识、输出稳定性、搜索批次、预览额度、发送结果确认、登录态恢复和页面变化时的失败行为。
