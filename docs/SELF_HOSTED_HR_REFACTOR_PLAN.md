# Boss-Forge 纯自研 HR 控制面重构设计

> 决策日期：2026-09-01
>
> 结论：停止使用 Odoo 运行时和 Addon，Boss-Forge 自己承担 HR 控制面、业务数据和招聘流程。

## 1. 重构目标

HR 只访问 Boss-Forge Web，不需要进入第三方 ATS。系统围绕“部门—岗位—规则版本—筛选任务—候选人岗位状态—审核—联系—审计”形成单一闭环。

本次不是照搬 Odoo 源码，而是吸收成熟 ATS 的通用产品思想：

- 岗位是招聘配置和权限的核心聚合。
- 同一个自然人可以关联多个岗位，并在各岗位拥有独立状态。
- 招聘过程使用可配置阶段、负责人、协作者、待办和操作记录。
- 已发布规则、消息模板和联系策略不可原地修改，只能生成新版本。
- 外部副作用走任务队列、幂等键和审计，不由浏览器直接调用 BOSS。

## 2. 唯一控制面

Boss-Forge Web 按 HR 工作流划分为六个功能页：

| 页面 | 职责 |
|---|---|
| 工作台 | 我的待审核、任务异常、联系异常、岗位进度和快捷入口 |
| 岗位与规则 | 岗位负责人、协作者、BOSS 账号、规则版本、筛选来源与自动联系开关 |
| 任务与计划 | 立即执行、指定时间执行、周期计划、暂停、取消和运行进度 |
| 候选人 | 岗位人才池、筛选证据、当前英语级别、人工审核和跨岗位去重 |
| 联系中心 | 消息预览、授权、Fake/Real 状态、失败与不确定结果处理 |
| 审计 | 配置版本、审核、联系、任务和系统安全事件 |

3000 端口的 Web 不再是临时诊断面板，而是正式 HR 产品。命令行只用于登录、Worker 诊断、迁移和故障恢复。

## 3. 保留的现有能力

- 岗位新增与岗位级自定义规则。
- AND/OR、TEM8、985/211/双一流、经验、学历、技能、地点和全文关键词。
- BOSS 平台院校标签的任一/全部组合，不从学校名称推断。
- TEM8 多表达归一和未达标人员当前英语级别标注。
- 推荐牛人和搜索两种来源。
- 立即筛选、单次定时、工作日、每天和每周计划。
- 简历预览、截图、腾讯云 OCR 和规则证据。
- 人工审核、消息预览、联系意图、幂等、限额、时段、冷却和审计。
- 自动联系岗位开关继续保留；真实执行仍受独立总开关保护。

## 4. 从成熟 ATS 借鉴并自研的能力

### 4.1 组织与权限

- 部门、HR 用户、招聘负责人、面试官和管理员角色。
- 岗位负责人和协作者决定数据范围，管理员可跨部门查看。
- 数据权限在 API 查询层强制执行，不能只依赖前端隐藏。

### 4.2 招聘管道

- 默认阶段：新采集、待精筛、待审核、已通过、待联系、沟通中、面试、Offer、入职、淘汰。
- 阶段可按部门配置；关键阶段变化写入不可变审计。
- 候选人自然人档案与岗位申请分离，解决同一候选人跨岗位复用问题。

### 4.3 协作与活动

- 候选人和岗位支持备注、@协作者、附件和时间线。
- 支持跟进、面试、反馈和截止日期待办。
- 工作台按当前用户聚合逾期、今天和即将到期事项。

### 4.4 配置版本

- 规则、消息模板和联系策略使用 draft/published/retired 生命周期。
- 已发布版本不可修改；运行任务保存完整快照。
- 新版本支持基于历史候选人回放，展示命中变化后再发布。

### 4.5 分析

- 岗位漏斗、阶段转化率、筛选命中率、人工复核准确率和来源质量。
- 任务耗时、预览/OCR 失败率、联系成功率和异常积压。
- 指标只基于事件与岗位状态计算，避免前端临时拼数。

## 5. 自研架构

```text
HR Browser
    |
    v
Boss-Forge Web :3000
    |
    v
Control API :3100 ---- PostgreSQL
    |                    | positions / rule_versions
    |                    | candidates / candidate_position_states
    |                    | tasks / schedules / contact_intents / audit_logs
    |
    +---- screening queue ---- BOSS Worker ---- boss-cli / Chromium / OCR
    |
    +---- contact queue ------ Contact Worker (Fake by default)
```

Control API 是唯一业务写入口。Worker 只按租约领取任务，不直接决定岗位配置；Web 不保存规则真相，也不直接触发外部副作用。

## 6. 数据策略

Boss-Forge PostgreSQL 是唯一业务数据库。此前 Odoo 试验产生的兼容迁移和可空映射字段暂时保留，原因是不能修改已经执行过的历史迁移；它们不再由运行时代码写入，也不需要第二个数据库。待所有内网环境升级并完成备份后，再通过单独迁移清理废弃表和字段。

本机没有发现 Odoo 容器或 Odoo 数据卷，因此本次没有第三方库数据需要导入或销毁。现有 Boss-Forge PostgreSQL 卷必须保留。

## 7. 交付阶段

### S0：去除运行时依赖（本次）

- 删除 Odoo Addon、专用同步进程、入站 API 和双数据库部署。
- 自研 Web、API、单 PostgreSQL 和 Worker 成为唯一拓扑。
- 保留全部已有岗位筛选、审核、联系和审计能力。

### S1：部门级使用

- 用户、部门、岗位协作者和服务端数据权限。
- 招聘阶段配置、候选人时间线、备注与待办。
- 岗位规则模板和版本回放。

### S2：招聘运营

- 面试安排与反馈、Offer/入职状态。
- 跨岗位候选人运营、回复同步和人才库标签。
- 漏斗、准确率、来源质量、Worker 健康与异常告警。

### S3：受控真实联系

- 在 Fake 验收、账号健康源和业务授权全部通过后，另行设计 Real Worker。
- 岗位自动联系开关不能绕过全局熔断、限额、时段、冷却和不确定状态人工核验。

## 8. 当前边界

- 本次移除第三方运行时，不等于 S1/S2 全部完成。
- 当前不配置公网域名、TLS、CDN、WAF 或公网数据库。
- 当前没有真实联系服务，真实打招呼执行数保持为 0。
- 不实现绕过验证码、平台风控或产品额度的能力。
