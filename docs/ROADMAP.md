# Boss-Forge 自研产品路线图

> 原则：借鉴成熟 ATS 的业务模型，不引入第三方 ATS 运行时。

## 1. 已完成基础

当前已经有岗位、版本化规则、筛选任务、候选人岗位状态、证据、人工审核、消息模板、Fake 联系、Outbox 和审计。这些能力继续演进，不重写。

## 2. R1：部门使用基础（最高优先级）

目标：让多个 HR 在同一内网系统中安全工作。

- 用户、会话和密码/企业身份登录。
- 部门、HR、招聘负责人、面试官和管理员角色。
- 岗位负责人及协作者。
- 服务端岗位数据权限，不只做前端隐藏。
- 当前用户审计身份替换固定 `hr:dashboard`。
- API 分页、筛选和排序，替换完整快照前端分页。
- 操作冲突和权限拒绝的浏览器 E2E。

退出标准：两名 HR 只能看到各自岗位，负责人可协作，管理员可审计全部岗位；跨岗位越权测试失败关闭。

## 3. R2：招聘管道与协作

目标：从筛选工具升级为日常招聘工作台。

- 可配置阶段：新采集、待精筛、待审核、已通过、待联系、沟通中、面试、Offer、入职、淘汰。
- 候选人时间线、备注、附件和 @协作者。
- 跟进、面试、反馈和截止日期待办。
- 面试官反馈表和阶段推进权限。
- 同一自然人的跨岗位档案与申请视图。
- Do-Not-Contact 和淘汰原因。

退出标准：一个候选人可以在两个岗位拥有不同阶段，所有阶段变化和协作行为可追溯。

## 4. R3：规则运营

目标：让 HR 不写 JSON 也能安全管理复杂规则。

- 任意嵌套 AND/OR/NOT 的可视化规则树。
- 部门规则模板和岗位继承/覆盖。
- Draft/Published/Retired 生命周期与审批。
- 基于历史候选人的版本回放和差异报告。
- 可选规则权重、阈值和人工复核策略。
- 服务端规则列表、版本比较和回滚入口。

退出标准：发布前能看到新旧规则对同一历史样本的命中变化，已发布版本不可修改。

## 5. R4：通用语义筛选层

目标：让不同岗位能够处理缩写、别名、行业术语和上下文经历，而不为每个岗位单独编写识别代码。

- 建立跨岗位规范事实模型，覆盖证书、技能、职能、行业、项目、管理范围和业务结果。
- 条件执行模式支持平台标签、确定性规则、归一化实体和语义评分标准。
- 建立版本化同义词/语义目录；常见表达优先使用低成本确定性归一化。
- 对未识别、歧义和上下文型内容调用内网大模型，输出严格结构化事实和原文证据。
- 模型、提示词、语义目录、评分标准和阈值全部版本化，并与候选人快照一起回放。
- 无证据、低置信度、冲突和格式错误统一进入人工复核。
- HR 纠正沉淀为评估数据集和待审批的目录/规则变更，不在线自动修改生产判断。
- 建立按岗位和条件类型分层的准确率、召回率、人工纠错率、未知率和模型成本评估。
- 模型先以影子模式运行并与 HR 结论对比，达到岗位约定阈值后才允许影响筛选结果。
- 禁止模型推断 BOSS 学校平台标签或岗位无关的敏感个人属性。

退出标准：固定历史简历集可对同一版本稳定回放；每个语义结论都有原文证据；低置信度不自动通过或淘汰；模型关闭时确定性规则仍可运行。

## 6. R5：招聘运营与 BOSS 回复

目标：覆盖联系后的招聘运营。

- BOSS 回复和会话摘要同步。
- 人才库标签、跨岗位推荐和重复联系提示。
- 招聘漏斗、来源质量、规则准确率、OCR 失败率和 Worker 健康。
- 逾期待办、任务失败和账号异常告警。
- 数据导出与留存策略。

退出标准：HR 不需要切换到技术日志即可发现任务、账号和候选人流程异常。

## 7. R6：受控自动联系

目标：在人工阶段准确率与业务授权通过后，按岗位开启自动联系。

前置条件：

- R1 权限与审批完成。
- 权威 BOSS 账号健康数据源。
- 全局、岗位、任务三级开关可操作并可审计。
- 额度、时段、冷却、去重、熔断和紧急停止验收。
- Do-Not-Contact 与撤销授权实时闭环。
- Real Worker 独立部署、灰度账号和不确定结果人工核验。
- 真实副作用测试获得对具体范围的明确授权。

退出标准：关闭任一级开关都不能创建或执行自动联系；超时/崩溃不重复发送；紧急停止演练通过。

## 8. 暂不计划

- 公网 SaaS、多租户计费和公共注册。
- 绕过验证码、风控或平台额度。
- 自建第二套 BOSS 页面抓取。
- 用学校名称推断 BOSS 985/211/双一流平台标签。
