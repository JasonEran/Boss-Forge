# BOSS 账号切换与岗位恢复

> 适用于换账号扫码后岗位列表变化、规则丢失感知或 `BOSS_JOB_NOT_FOUND`。当前操作流程，非自动迁移能力声明。

## 为什么同名岗位不能直接续跑

系统按逻辑 BOSS 账号与 BOSS 岗位 ID 保存岗位。当前部署复用一个浏览器会话和 `boss-account-01` 逻辑标识；这个标识**不是已验证的 BOSS 手机用户身份**。换手机账号不会自动创建独立的一套运行环境。

任务创建时保存 `source_job_id`、岗位名称、规则版本及官方筛选快照。另一个账号的同名岗位可能有不同 ID。岗位同步会导入新 ID、暂停完整目录里未找到的旧岗位，但不会把旧任务改指向新岗位，也不会自动复制规则、计划、联系开关或历史候选人。

这是保护历史归属的边界，不能靠放宽成“按名称猜岗位”修复。

## 切换前

1. 记录需继续的岗位、任务、规则版本、计划时间、人数目标和自动招呼设置。
2. 停用相关未来计划；对已存在的任务按实际需要取消或等待完成。计划停用不会撤销已经创建的任务。
3. 暂停相关岗位联系执行，等待进行中的单次动作结束。若有 `uncertain`，先在原账号核验回执。
4. 使用现有登录流程由本人切换账号，保留原浏览器卷；不要复制 profile、清空 Cookie 或重建登录卷。

## 切换后

1. **确认登录**：控制台 `authenticated`、浏览器认证和 Worker 心跳就绪，运行版本/策略一致。
2. **同步岗位**：获取完整目录。核对当前开放岗位的名称、地点、薪资及 ID；出现同名项时逐一确认。
3. **明确映射**：记录“旧内部岗位 / 旧 BOSS ID → 新内部岗位 / 新 BOSS ID”，由业务语义核实对应关系。没有可靠对应就停止该岗位的迁移。
4. **准备规则**：保留旧规则，给新岗位创建新版本；获取新岗位的官方选项快照，逐项检查可用性，不复用另一个岗位的 `optionsSnapshot.bossJobId`。任何业务条件调整需明确记录；草稿不等于已发布。
5. **补齐权限和执行设置**：核对新岗位负责人、协作者、联系控制及暂停状态。不得因旧岗位允许联系就假定新岗位自动继承。
6. **重新安排任务**：在新岗位使用已发布规则，按确认的人数和自动招呼设置创建新任务；使用幂等键避免重复安排。旧失败任务保留，不改它的来源快照。
7. **恢复未来计划**：按确认的频率、上海时间和目标新建计划；旧计划保持停用，防止次日重复生成。
8. **验证**：确认新任务 `source_job_id` 是新岗位，发生真实进度，查看具体等待原因。成功招呼以本任务 `contact_intents` 的 `greet + sent` 为准。

多个岗位分别做完第 3–8 步。恢复了一个岗位不代表另一个已排队。

## 当前可用入口及限制

- 岗位同步：`POST /api/boss/positions/sync`。
- 新岗位选项：`POST /api/positions/:id/boss-filter-options`。
- 新规则版本：`POST /api/positions/:id/rules`；权限允许时可发布。
- 任务与计划：`POST /api/tasks`、`POST /api/schedules`；创建需 `Idempotency-Key`。
- `POST /api/positions/:id/boss-binding` 仅用于**尚未绑定 BOSS ID 的旧岗位**，且来源导入岗位必须无业务配置。它不是已绑定岗位换账号的重绑接口。

界面没有完整的“跨账号一键迁移”向导。运维需要补齐配置时应走已有鉴权 API，并保留映射、备份和审计；不得直接改库覆盖原任务或合并候选人历史。重试旧任务会继续使用原任务身份，不能解决 ID 改变。

## 验收清单

- 当前账号和新岗位来源已经确认。
- 原岗位/规则/任务/候选人历史仍可查询。
- 新规则已发布，快照属于新岗位；未批准草稿没有执行。
- 每个需要恢复的岗位都有独立新任务，目标及自动招呼设置正确。
- 新计划与旧停用计划没有重复启用。
- 无重复外部联系；待核验结果没有被自动重发。
