## 二、当前真实业务流程

实际系统的主流程如下：

1. 管理员/HR 登录控制台，从工作台或岗位页选择部门与岗位。
2. 新建或编辑岗位，维护岗位说明和联系消息模板。
3. 在同一个岗位弹窗中发布新规则版本：年龄、性别、毕业年份、学历、工作年限、院校标签、CET-6/TEM-8 等；可生成、预览及应用语义同义词。
4. 创建推荐或搜索任务；M1 worker 在工作时段领取任务，通过持久化的 BOSS 浏览器会话获取候选人卡片。
5. worker 按简历查看策略打开简历、截图、OCR/文本提取，执行结构化规则与语义影子判断，写入候选人状态、证据和置信度。
6. HR 在候选人页按任务查看候选人，展开规则证据并人工审核。
7. 审核通过的候选人可进入联系页预览消息；按产品意图应再人工确认，然后由联系 outbox/worker 幂等发送。
8. BOSS 登录、运行中心、团队策略、自动化、分析和审计页提供辅助状态与控制。

这条流程“形状”已经齐全，但目前有四处关键断裂：

- 同一候选人再次出现时会被迁移到最新任务，旧任务结果人数缩水，且新任务可能继续沿用旧规则的判断与证据。
- 简历处理首轮 15 人仅 6 人完成，10 次出现空白/OCR 不可用或 source expired；重试尚未经过下一个工作时段验证。
- 联系安全控制有两套数据源且没有真正串到同一发送前置检查，当前真实发送又已启用。
- 页面显示的工作时段、登录健康、自动化模式等与实际 worker 状态不一致。

## 四、用户体验问题（按优先级）

### P0：正式使用阻断

1. **界面明确误导真实联系模式。** 全局页头显示“真实打招呼已开启”，自动化页却同时写“Fake-only”“不会执行真实打招呼”“realGreetingExecuted 永远为 false”。现场环境和进程证明真实 worker 已开启。HR 无法据此判断一次确认是否会触发真实外部联系。
2. **历史任务不再是可信记录。** 候选人页选择首个任务时，页头显示“任务采集 15”，列表实际只有 8 个待审核加 1 个失败；DB 中该任务仍有 15 个 snapshot，但仅 9 个 candidate state 仍指向它。按任务审核和追责闭环因此失真。
3. **登录与运行健康可能假绿。** 登录页显示 authenticated 和 worker 已启动，但 DB 最后权威健康检查停在 19:18，heartbeat 停在 23:50:33；supervisor 不持续检查当前 BOSS 页面。登录失效后 HR 可能继续等待，而系统没有可信的下一步提示。
4. **运行环境已实际 OOM。** 主机只有 3.3 GiB、无 swap；boss-login 约 1.19 GiB/237 PIDs，Web 约 418 MiB，容器无 memory/pids limit。内核已杀死 Chromium 与 Web `workerd`，Web 有两次重启。正式工作时会表现为页面中断、worker 停顿或登录页面消失。
5. **配置漂移导致页面与真实节奏不一致。** 团队页从 API 显示 09:00–18:00，M1 实际按 09:00–20:00 工作，DB 证明 19 点仍查看 15 份简历。用户无法依靠页面判断风控节奏。

### P1：明显降效或造成错误判断

1. **等待/失败状态没有告诉 HR 为什么以及何时恢复。** 任务只显示“完整简历精筛”或 `screening`；10 次实际失败没有在运行告警中形成可操作提示，页面也不区分等待工作时段、等待额度、卡片过期、OCR 重试和需人工处理。
2. **常见简历表达会误判。** `2026届` 未识别，`99年毕业` 被解析为 2099；“最高学历：硕士”加教育历史可能被判学历冲突。年龄/毕业年份也不能稳定从 OCR 全文提取。
3. **缺少直观的应届设置。** HR 只能理解“最晚毕业年份”和工作年限组合，不能直接回答“接受 2026 届/仅应届/不限”。
4. **人工审核不能纠正规则误杀。** 对已经被规则判定未通过的候选人，审核通过/拒绝按钮被禁用；一旦解析错误，HR 没有清楚的覆盖与留痕路径。
5. **候选人详情暴露内部实现。** 浏览器实际看到 `cet6 positive`、`missing_graduation_year ambiguous`、`missing_field`、`semantic_unknown`、原始 JSON 数组和大段未格式化文本，不能算“普通 HR 能理解的解释”。
6. **岗位/任务选择器泄漏 UUID。** 收起状态直接显示 `86ad...` 一类内部 ID；展开项虽有人类标签，但第一眼不知当前选了什么。
7. **页面先闪现错误空状态。** 任务、运行、分析等页面在异步请求返回前短暂显示 0、无岗位、Fake-only 或无任务，而不是明确 loading；安全模式和真实状态尤其不应先猜默认值。
8. **全局仪表盘可能拼接两个岗位的数据。** 当前岗位来自用户选择，任务进度来自全局最新任务，岗位 A 可显示岗位 B 的任务进度。

### P2：可边使用边优化

1. 主导航有 7 个一级入口，实际还包含任务、候选人、流程、联系、自动化、BOSS 登录、运行、分析、团队、审计等多个心智模型；普通 HR 很难知道任务、候选人和流程三页的边界。
2. 流程页同时提供九阶段、备注/@、DNC、跟进任务、面试和附件，远超当前小团队筛选闭环；状态又显示 `screening`、`insufficient`、`not_matched`、`not_required` 等内部枚举。
3. 分析页将任务 snapshot 数和唯一候选人 state 混合展示，例如来源 30、漏斗 24，未解释为何不同。
4. “额度归零”没有确认及风险说明；“同步回复”允许手工输入候选人回复并进入权威数据；“记录健康状态”允许人工写入所谓权威账号健康。这些名称和权限都容易误导。
5. 团队页暴露 stage ID、排序、terminal 等技术配置；审计页大量显示原始事件码和对象类型。应转为管理员低频入口。

## 五、业务逻辑与数据一致性问题

### 1. 候选人身份、任务归属和规则证据

- 身份回退使用展示姓名加原始“信息”摘要，没有优先使用稳定的 `boss_geek_id`/source locator；同名同摘要的人可能被合并，已有人的信息变化又可能产生新 fingerprint。
- upsert 冲突时覆盖 `latest_task_id`、`latest_snapshot_id`、`rule_version_id`，但已 screened 的候选人会保留旧 decision、confidence、English/evidence 和 review state。于是“新任务 + 新规则版本”可以展示旧任务结论。
- 页面按 `latest_task_id` 分组，导致旧任务人数随新任务抓取而缩水。任务 snapshot 虽保留，但不再是可审核的逐任务结果。
- worker 每轮仍从同一推荐/搜索入口抓取，没有分页或排除历史候选人。两轮各 15 人却重复 6 人，未实现“尽量获取新人”。
- 多个外键分别合法，但数据库约束没有保证 rule version 属于该 position、task 与 position/rule 对齐、evidence 对应特定 snapshot/rule version。

关键代码位置：`packages/data/src/repository.ts:499`、`:554`、`:646`、`:678`，`packages/m1-core/src/index.ts:50`，`apps/boss-worker/src/m1.ts:257`。

### 2. 真实联系安全与幂等

- 当前 worker 按候选人姓名执行 greet/chat，而不是用已校验的 stable locator；重名时可能联系错误对象。
- 一次 dispatch 会先执行外部 greet，再进入聊天发送模板正文。若 greet 成功、后续普通错误，attempt 可被标记 failed，重试可能再次打招呼。
- do-not-contact 只在创建 intent 时检查，dispatch 前不重新检查；HR 在排队后标记 DNC 仍可能被发送。
- 自动化页写入 `contact_controls.emergency_stop`，真实 dispatch preflight 却读取旧的 `contact_settings.emergency_stop`。页面紧急停止不能保证拦住已排队真实联系。
- 页面与 API 的角色校验不足：任务、重排、审核、联系意图等关键动作只校验岗位访问，未统一限制为 recruiter/manager；岗位 POST 甚至先创建记录，再执行 manager-only adopt，未授权请求也可能先写库后返回 401。

关键代码位置：`apps/boss-worker/src/contact-worker.ts:85`、`:128`，`apps/boss-worker/src/contact-dispatch.ts:45`，`packages/data/src/m2-repository.ts:909`，`packages/data/src/department-repository.ts:1169`，`apps/control-api/src/server.ts:717`、`:903`。

### 3. 规则与语义判断

- 语义“90% 准入”把所有 aliases 展平做 substring 匹配，忽略 criterion、canonical value、否定、rubric、模型输出及最小样本量；一个全命中样本就可能开启 active。
- position semantic mode 为 off 时，engine 可写 `runtime_mode=off`，DB check constraint 仅接受 shadow/active，命中特定路径会事务失败。
- 规则 retirement 只改 lifecycle，不清 active version；创建任务也未检查该 active version 是否 retired。
- 985/211 的“只认显式标签、不根据学校名猜测”本身是正确的，但缺标签时 UI 可配置成直接不通过，不利于人工复核。

### 4. 指标、运行状态与权威口径

- Dashboard 当前岗位与全局最新任务独立取值，可能拼接不同岗位。
- “今日已联系”先算日期口径，随后又被当前候选人全部 sent 数覆盖。
- 分析页 30 来源记录是两个任务 snapshot，24 漏斗是唯一候选人 state，未说明口径差异。
- 运行中心允许用户手工输入“候选人回复”并写入权威 inbound reply，也允许手工记录“BOSS 账号健康（权威数据）”，会污染真实指标。
- `account_health` 已陈旧、heartbeat 不更新，但页面继续显示 authenticated；实际 OOM/OCR/source expired 又没有 operational alert。
- migration 仅记录文件名、无 checksum；远端 `/opt/boss-forge` 没有 Git revision，且 boss-login 镜像比 API/Web 新，部署无法可靠复现。

## 六、运行稳定性与恢复能力

正向证据：

- PostgreSQL 当前约 11 MB、4 个连接、无等待锁；22 个 migration 均已应用。
- task/position/candidate/latest snapshot 等基础外键巡检未发现悬空记录。
- 6 个已完成筛选记录均有非空截图文件、hash 和完成时间。
- 简历策略的 45 秒下限和小时额度在本轮真实记录中得到遵守。
- 浏览器 profile、boss-cli、runtime、PostgreSQL 都使用命名 volume，当前登录确实跨容器重建保留。

阻断证据：

- 15 个简历首轮只有 6 个完成；10 次失败虽已重排，尚未证明次日能自动恢复。
- 主机已发生 OOM，Chromium 和 Web 进程被内核杀死；无 swap、无容器资源限制，且部署时同机构建镜像。
- Web 使用 `wrangler dev` 常驻，已经因连接中断退出并自动重启两次。
- 没有自动数据库备份任务，只有一份 9 月 3 日手工 gzip 备份；未做恢复演练。
- supervisor 的 healthcheck 只看状态 JSON 是否持续更新；状态 JSON 又由 supervisor 自己硬写，无法证明浏览器登录、Chromium 或 BOSS 页面真的可用。

## 七、测试与验收结果

本地安全测试均在以下外部能力关闭的环境运行：

```text
BOSS_FORGE_REAL_GREET_ENABLED=0
BOSS_FORGE_RESUME_PREVIEW_ENABLED=0
BOSS_RESUME_OCR=0
BOSS_FORGE_SEMANTIC_ENABLED=0
```

结果：

- 修复前审计当时的 `pnpm test`：42 个测试文件、262 个测试全部通过；这是历史快照，不是当前最新计数。
- `pnpm typecheck`：通过。
- `pnpm lint:web`：通过。
- 部署浏览器 E2E：实际页面、实际 API 与实际 DB 的只读主流程走查完成；岗位/规则编辑弹窗、任务切换、候选人证据、失败状态、联系页、自动化、登录和运行状态均检查。
- 真实联系 E2E：按红线在最终确认前停止，发送数为 0。

测试覆盖的限制：16/42 个测试文件主要是读取源码文本后断言字符串，并不证明行为正确。仓库的 `test:integration:data` 和 `test:e2e:user` 未执行，原因不是把它们简单指向生产库：本机 Docker daemon 不可用，也没有 `initdb`、PostgreSQL、Podman 或 Colima，无法建立一次性隔离数据库；更关键的是，两个现有脚本没有 `SKIP_CONTACT` 或可分段 dry-run 开关，前者会创建 fake/real contact intent、领取 dispatch 并模拟 uncertain，后者会创建联系意图、contact control 和批准审批请求，直接违反本次“不得创建、批准或执行联系任务”的红线。已用随机本地端口安全验证外部 `DATABASE_URL`/API URL 覆盖方式，不曾连接任何数据库。后续应先把 E2E 拆出完全不含 contact 的安全阶段，再用 API、migration、seed、测试进程共同绑定的一次性 PostgreSQL 运行。文档中“22 文件/179 测试”和 Fake-only 描述均已过期。

## 八、正式使用前必须修复

以下完成前，不建议普通 HR 正式使用：

1. **默认关闭真实联系。** 先将所有审计/演练环境设为 mock/dry-run；修复并统一 contact control、dispatch preflight、DNC 重检、角色权限、stable locator、greet/send 原子结果与 uncertain 处理后，才重新评估实发。
2. **建立真正的逐任务候选人结果。** 使用稳定 `boss_geek_id`/source identity；每个 task 保存独立 screening result、rule version、evidence 和 review，不再迁移单一 state；抓取时优先排除近期重复候选人。
3. **修复权限的先写后验。** 所有 mutation 先鉴权和校验 scope，再进入事务；任务、审核、联系、重排及控制开关需要最小明确角色。
4. **消除部署与配置漂移。** API/Web/worker 必须作为同一 revision 原子部署，启动时校验关键配置一致；页面展示 worker 实际策略，而不是 API 自己的旧环境。
5. **修复运行资源。** 增加内存余量或 swap，禁止业务时段同机构建，给 Chromium/Web 设置合理资源与 PID 上限，将 Web 改为稳定生产运行方式。
6. **让登录健康可验证。** 周期检查 CDP 可达、当前页面不是登录/验证/风控页，持续更新 worker heartbeat；状态失效时停止 BOSS 任务并给 HR 一条明确恢复路径。
7. **修复高频字段识别。** 覆盖 `2026届`、两位数毕业年、最高学历与教育历史、OCR 全文中的年龄/毕业年份；无法确定时进入人工审核而不是直接失败。
8. **验证失败恢复闭环。** 在下一个安全工作时段确认 10 个重排任务能恢复；卡片过期、内容未完整加载、OCR 失败必须在 UI 区分原因、自动动作、下次重试和人工按钮。
9. **统一并收紧语义准入。** shadow 保持只读；以足够样本、逐准则准确率、否定与 unknown 覆盖评估 active，修复 runtime mode constraint。
10. **增加简单备份。** 每日 PostgreSQL 备份、保留周期和一次可验证恢复即可，不需要引入复杂灾备平台。

## 九、可以边使用边优化

- 所有技术状态翻译为中文行动语句，例如“等待明日 09:00 自动继续”“候选人卡片已失效，系统将在列表刷新后重新定位”“OCR 失败 2/3，下一次重试……”。
- 选择器显示“日期 · 岗位 · 类型 · 人数”，不显示 UUID。
- 候选人证据默认显示一句通过/未通过原因，原始 JSON 和 OCR 全文放入“技术详情”。
- 让 HR 能对规则误判执行“人工改判”，要求填写原因并保留原机器结论。
- 将 OOM、连续 OCR 失败、heartbeat 陈旧、配置漂移形成少量可操作告警。
- 自动化降低 contact idle 的 2 秒日志噪音，页面显示部署 revision。
- 将“额度归零”改成“重置本次软额度（不改变今日实际查看数）”，加确认且仅管理员可见。
- 将“同步回复”“记录权威健康”降级为不计入业务口径的联调/备注能力，并改成不会暗示权威性的名称。

## 十、页面合并、按钮改名与自动化建议

> 本节的“四个一级导航/先隐藏高级功能”是修复前初始建议，已由第十五节的正式产品决策修订：合理能力保留，只合并重复入口，并用角色、Tab 和渐进展开控制复杂度。

普通 HR 的一级导航建议从当前多个模块收敛为四个：

1. **工作台**：只显示“当前该做什么”、正在运行的任务、需要人工处理的失败与待审核数。
2. **岗位与规则**：合并岗位资料、筛选规则、语义同义词和消息模板；一个岗位只保留一个编辑入口。
3. **任务与候选人**：合并任务、候选人和流程，以任务为筛选器，在同页切换“待处理/通过/未通过/失败/已联系”。九阶段、面试、附件、@ 和跟进任务先隐藏为高级功能。
4. **联系与系统状态**：联系预览与登录/风控状态放在一起；真实联系修复前只开放 dry-run。运行、分析、团队和审计移到管理员抽屉，普通 HR 不作为一级导航。

建议把普通导航中的旧 `/rules`、`/semantic` 能力收进“岗位与规则”，兼容路由继续保留；自动化页在真实/假模式和安全开关统一前先强制 dry-run，并收进高级设置。Operations 与 Analytics 在普通 HR 入口合并成一个“运行状态”，原有明细能力继续供管理员展开。

建议按钮和状态文案：

- `screening` → “正在获取并检查简历”
- `insufficient` → “资料不足，等待重试/人工补充”
- `not_matched` → “不符合规则”
- `semantic_unknown` → “语义判断不确定，不影响当前结论”
- “保存并立即生效” → “发布新规则并用于新任务”，明确不回写历史任务
- “检查登录状态”应显示最近真实验证时间与验证内容，而不是只显示 worker 存活
- 发送确认应明确“将联系 1 位候选人、姓名/岗位/消息正文”，且默认不勾选、不可批量隐藏细节

适合自动化的只有三类：自动选择当前岗位的 active 规则；自动排除近期重复候选人；自动将可恢复失败按有限次数重试并说明进度。不要自动批准联系，也不要把不可确定字段自动判失败。

## 十一、不建议开发的非必要功能

- 微服务拆分、消息中间件、复杂工作流引擎和企业级审批链。
- 更多角色层级、矩阵权限、跨公司多租户。
- 完整 ATS 的 offer、入职、人才库营销、组织编制、绩效等模块。
- 更多九阶段看板、面试日历、附件中心、@ 协作、跟进任务，除非小团队真实使用证明需要。
- 更复杂的 BI 大屏、可配置指标平台或通用语义治理后台。
- 在基础字段、逐任务结果和真实联系安全未可靠前继续扩充 LLM 标签、自动外呼或批量联系。

## 十二、是否功能过多、入口重复或概念复杂

> 本节描述修复前状态。最终方案不以删除功能为目标；详见第十五节与第十七节。

**是。** 当前并不是因为少一个功能而不够用，而是核心对象和安全状态尚未统一，同时已经叠加流程、自动化、运行、分析、团队、审计、面试、附件、DNC、跟进、语义治理等多个概念。重复入口和两套 contact control 已经不只是 UX 问题，而是直接造成“页面紧急停止不控制真实 dispatch”的安全缺陷。

最合理的方向是删减入口、统一状态源、修复逐任务数据模型和发送前置检查。等普通 HR 能稳定完成“一岗一规则一任务一批候选人一轮审核一次人工确认”后，再依据真实使用痛点增功能。

## 十四、最终验收结论

**目前不够用。**

系统已经具备可辨认的招聘辅助产品骨架，规则编辑、节奏控制、证据展示、影子语义和持久化登录也有若干扎实基础；但当前仍存在会阻断日常工作或带来误发/风控风险的缺陷：逐任务候选人结果不可信、真实联系安全链未闭合、鉴权顺序错误、页面与 worker 状态漂移、登录状态可能假绿、简历首轮完成率低且恢复未验证、远端已经发生 OOM。

因此现在不适合交给普通 HR 正式使用。建议先以**真实联系关闭的内部试运行**方式，只验证岗位—规则—任务—候选人—人工审核闭环；完成“正式使用前必须修复”的 P0 项并跑通一轮可恢复的 mock E2E 后，再做正式验收。

### 决策二：保留合理功能，补齐缺口

因此，后续信息架构目标是“能力保留、入口清楚、默认简单、需要时展开”；工程目标是先保证每项已展示能力真实可用，再增加确有日常价值的功能。

## 十六、本地修复后、生产部署前复验（2026-09-04）

> 本章节记录同日的本地修复、隔离数据库和浏览器证据。前述“目前不够用”、远端现场数据和问题列表保留为**修复前审计快照**；随后完成的生产部署见第十七节。完整修复矩阵和证据见 [Boss-Forge 修复与复验报告](REMEDIATION_REPORT_2026-09-04.md)。

### 复验范围与边界

- 复验对象是本地共享工作树、一次性隔离 PostgreSQL 和本地浏览器，不是远端服务器的新部署。
- 远端没有应用本轮代码；没有重启远端 BOSS Worker、Web 或数据库，也没有触碰远端浏览器登录目录和数据卷。为落实零发送红线，仅通过现有管理 API 将 global 和可见 department 控制关闭并设为 emergency stop，同时把磁盘环境文件的真实联系开关改为 0；运行容器仍保留旧值，需受控重建后才生效。
- 浏览器验收停在最终消息预览后点击取消；没有创建、批准、领取或执行联系任务。
- BOSS 登录页只做只读状态检查，显示 Worker 离线/运行状态不一致；没有刷新二维码、导航 BOSS、退出登录或尝试重新登录。

### 关键修复结果

1. 真实联系增加不可绕过的编译期总闸，当前 `REAL_CONTACT_TRANSPORT_AVAILABLE=false`。环境变量、页面开关、授权审批、M0 诊断和 Worker 都不能打开真实发送。
2. migration 023 将候选人状态修正为逐任务事实，回填历史任务、重算任务计数，并用数据库触发器约束 task、position、rule、snapshot、evidence 和 contact 归属。
3. migration 024 将旧 active 全部降为 shadow，并把岗位语义模式约束为 off/shadow。旧的 alias substring 评估不再可能进入正式招聘判断。
4. 写接口统一先鉴权后入库；未认证返回 401，已认证但无权限返回 403。任务取消/重试、审核等使用幂等键和乐观版本。
5. BOSS 会话通过精确 zhipin.com 域名和只读 DOM 信号判断；登录、验证、风控、浏览器、release、简历策略或心跳不一致会暂停 Worker，不会自动刷新二维码。
6. 浏览器和 boss-cli 登录数据改为必须显式指定的 external volume；预检验证卷、挂载名和并发容器，禁止用新卷、复制或重建登录目录试错。
7. Dashboard 按授权岗位/部门过滤，当前岗位只配对本岗位任务；“今日已联系”保留数据库 sent-only 口径。
8. HR 页面支持应届、年龄、毕业年份、性别、学历、CET-6/TEM-8 OR、人工改判、失败原因和下一步说明；技术 JSON 与版本信息折叠。

### 修复后剩余限制

- 远端仍为 22 个 migration，旧 `boss-login` 容器中仍有 real contact worker 进程且运行环境值为 1；当前由 global emergency stop 绝对阻断，不能把磁盘配置已改为 0 误认为容器已经安全升级。远端没有 queued/approved/processing/ready 联系任务。
