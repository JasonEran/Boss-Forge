# 扫码服务异常与刷新恢复修复（2026-09-14）

生产版本：`boss-login-refresh-20260914`。

## 原因

服务器 Chromium 仍有 BOSS 沟通页面，但会话检查出现 `Page.enable timed out`。Supervisor 停止 Worker 后进入等待恢复循环，只检查已登录状态，没有消费前端已接受的刷新请求；观察到 15:09 的刷新请求仍留在运行目录。浏览器处于连接异常时，用户刷新无法让它重新建立连接。

## 修复

- Worker 完成退出后消费手动刷新请求。可读的已登录页或登录页重新进入登录流程；连接仍不可用时受控重启容器中的 Chromium，保留浏览器资料卷。
- 请求通过原子重命名领取，一次刷新只消费一次，处理旧请求时不会删除新请求。登录成功后清理已完成的刷新请求，避免在后续故障中重放。
- 登录 relay 的错误状态也支持刷新后重新建立浏览器连接。对 Puppeteer 失败连接可能残留的传输句柄，使用明确退出码确保重启；父进程先等 Worker、IPC 和正在分析的简历结束。
- 二维码刷新失败后保持错误状态，避免下一次心跳又显示等待扫码但实际没有可用图片。浏览器初始化失败的重试受时间约束。
- 遇到已记录或新发现的安全验证状态继续暂停。

## 验证与部署

- 生产镜像通过类型检查、140 个测试文件共 1009 项测试、Web lint 和构建。
- 断网隔离容器内运行真实 login relay，使用本地模拟 CDP 重现连接失败及遗留传输；写入刷新请求后约 510 ms 以退出码 75 完成退出，请求已消费。没有连接外部网站或发送聊天消息。
- 15:14 受控重启后扫码页面恢复；15:26 已观察到用户完成登录。15:30 新版本部署后 API、Web、扫码服务均健康，BOSS 已登录，API/Worker 版本一致，实时沟通连接正常。为保留用户已完成的登录，生产验收未再次要求刷新二维码或退出账号。
- 没有数据库迁移，持久化数据卷不变。服务器仅调整镜像及发布版本配置；OCR 等其余配置保留。
- 部署初次预检提示磁盘低于 8 GiB。确认旧 speed 版本镜像仍在后，移除其重复的完整镜像归档约 1.4 GB，保留该版本 Docker 镜像、数据库和配置备份，再完成部署。

服务器证据目录：`/opt/boss-forge/backups/boss-login-refresh-20260914`。
