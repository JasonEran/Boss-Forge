# 核心业务逻辑复核 · 2026-09-07

检查版本：`boss-jobs-20260907-1310cst` 对应代码与 Linux amd64 应用镜像。范围为岗位同步/选择、规则编辑发布、任务/计划调度、负责人分配、联系岗位来源。

本轮发现 **5 个确定缺陷及 1 个调度策略问题**。本报告仅记录检查和复现，未修复这些问题或改动生产服务。未连接真实 BOSS 页面、查看真实候选人或执行联系动作。

> 后续进展：`screening-fix-20260907-1440cst` 已修复第 1 项回调问题，并隔离第 2 项调度异常对精筛/即时任务的影响；过期规则计划本身及其余事项仍待单独修复。详见 [筛选修复记录](SCREENING_FIX_2026-09-07.md)。

## 1. P1：新增岗位读取回调在实际运行方式下失败

位置：`apps/boss-worker/src/boss-jobs-browser.ts:15`、`:67`；入口 `boss-jobs.ts:62` 使用 `node --import tsx`。

`readJobPage`、`readJobOptions` 传给 `frame.evaluate` 的回调内部有命名箭头函数。当前 tsx 转译后产生对 Node 模块内 `__name` helper 的引用。Puppeteer 将函数本身序列化给浏览器，不会一并带入模块 helper，回调因缺少 `__name` 报错。

在生产对应 Linux 镜像 Node v22.23.2 中，取得真实转译回调，在独立 JavaScript 上下文内执行，两个入口均得到：

```text
v22.23.2 job catalog ReferenceError: __name is not defined
v22.23.2 job dropdown ReferenceError: __name is not defined
```

影响：登录后同步岗位仍会失败；已绑定岗位读取推荐下拉的同一写法也不可用。目录读取循环捕获异常，外部更可能显示通用“未读取到列表”提示，而非原始 helper 错误。这不是仅靠重新扫码能够解决的问题。

这是上一轮新增代码的遗漏。609 项测试主要覆盖纯逻辑、通信替身和数据层，Linux 检查只导入模块，未执行序列化后的浏览器回调。

修复方向：使用完全自包含的浏览器脚本，并在真实转译运行方式下验证回调执行；然后再做真实 BOSS 页面验收。

## 2. P1：发布新版规则使旧定时计划持续失败，并挡住其他工作

位置：`packages/data/src/m2-repository.ts:289`、`:389`；`department-repository.ts:1003`；`apps/boss-worker/src/m1.ts:806`。

创建计划时固定 `rule_version_id`。发布 v2 会把 v1 置为 `retired`；计划到期仍用 v1 插入新任务，migration 023 的任务约束要求规则为 `published`，因此事务报错。计划仍启用且到期时间不变，下轮继续失败。

独立数据库复现：建立使用 v1 的每日计划 → 发布 v2 → 连续两次调度，均报 `task rule version must be published`；另一个健康到期计划也未生成任务。Worker 把计划调度放在精筛和即时采集之前，同一 try 块内的失败会跳过后续处理。

修复方向：明确新计划运行如何选规则，建议每次生成任务时取得当前发布版本再冻结到该任务；隔离单个计划的失败，记录具体计划告警，避免阻塞其他岗位。

## 3. P1：规则编辑往返会丢失或改变原条件

位置：`apps/web/app/position-rule-dialog.tsx:257`、`:339`、`:354`、`:521`、`:662`。

表单把规则树展开为叶子，只取同类条件的第一项，保存时重新拼成一层 AND/OR；每个叶子不同的缺失策略也归并为同一个值。英文证书保存固定为 `mode: any`。

直接提取并执行现有表单的初始化和保存代码，以 API 测试替身接收保存结果；未修改任何表单选项，得到：

- 原规则“20–35 岁，并且 Java 或 Python”变成“20–35 岁，并且 Java”，Python 条件和 OR 子组消失。
- 技能缺失策略从 `ignore` 变成年龄条件的 `fail`。
- 原“CET6 和 TEM8 都满足”从 `all` 变成 `any`。

触发范围：通过旧版、接口、模板或复杂规则配置产生的上述结构；不是说所有当前简单表单规则都会改变。

修复方向：未编辑部分保持原规则树语义；不能无损展示的规则应明确提示并保留原节点，不能静默转成简化规则。

## 4. P2：设置“负责人”没有真正完成负责人交接

位置：`packages/data/src/department-repository.ts:482`；团队页面 `apps/web/app/team/team-client.tsx:397`。

`assignPosition(..., 'owner')` 只改 `position_members.member_role`，不会更新 `positions.owner_user_id`。岗位创建任务时检查的却是后者。

独立数据库复现：原管理员建岗位 → 新招聘负责人被分配为岗位“负责人” → 实际 owner ID 仍是原管理员 → 新负责人停用原管理员 → 新负责人创建筛选任务失败，提示缺少有效负责人。

修复方向：把岗位负责人交接作为一致的数据操作，同时更新实际 owner、成员关系和展示信息；普通协作成员分配保留现有行为。

## 5. P2：多岗位 ID 未贯穿打招呼预览与联系前定位

位置：`apps/control-api/src/server.ts:81`、`:99`；`apps/boss-worker/src/contact-worker.ts:120`。

采集/精筛新增了 BOSS ID 绑定，但预览招呼语仍只传 `bossJobKeyword`，联系前恢复列表也调用旧关键词路径。

用安装版本的 `resolveEffectiveGreeting` 和两个同名、不同 ID 的岗位配置复现：按名称“运营”返回 `BOSS_GREETING_JOB_AMBIGUOUS`；按 ID `job-b` 则唯一成功。新岗位绑定 ID 没有传到这条路径。

影响：两个同名岗位可以同步为独立岗位，但后续招呼语预览仍不能唯一选择；相近名称下的联系前列表恢复仍有旧匹配行为。本轮没有执行真实联系，也不把潜在错选描述成已经发生的生产事故。

修复方向：将任务/岗位的 BOSS ID 贯穿到预览及联系前的只读岗位恢复，保持既有动作确认流程。

## 6. P2 策略问题：恢复后连续补跑过期定时计划

位置：`packages/data/src/m2-repository.ts:197`、`:402`。

下次执行时间基于旧执行时间推进，而不是当前时间。停机或岗位暂停数天后，计划可能连续多轮仍然到期，生成多个补跑任务；这些任务读取的是恢复时的推荐列表，不是过去几天的历史推荐。

独立数据库复现：每日计划首次执行时间设为 3 天前，连续 5 次调度生成 4 个任务。

这是确定的现有行为，是否补跑属于业务策略选择。对于推荐筛选，建议默认合并漏跑为一次，然后推进至未来时间，避免重复采集和重复精筛。
