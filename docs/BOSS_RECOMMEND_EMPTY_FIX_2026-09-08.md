# BOSS 无符合候选人与补充推荐修复

日期：2026-09-08。已发布版本：`boss-recommend-empty-20260908-1455cst`。

## 现象与根因

14:36 创建的「亚马逊运营」20 人任务在采集阶段失败，记录为 `BOSS_RECOMMEND_UNVERIFIED`，尚未读取简历或进入 AI 评分。

现场复现：官方第一页 HTTP 200、业务 code 0、岗位 ID 正确，但成功空列表省略 `zpData.geekList`，并带有 `page: 1, hasMore: true`。BOSS 自行请求第二页并展示 15 位补充推荐；原生 CardList 在这批人之前插入 `cardType: memo, type: 1` 的分隔行，显示“暂无符合牛人，更换筛选范围试试”。此前代码把缺少数组误判成接口失败，也没有排除补充推荐。

另一条实际路径是第一页只有 13 位符合条件的候选人，BOSS 自动追加第二页 15 位补充推荐。等待渲染时如果要求整个列表与第一页完全相等，也会错误超时。

## 筛选范围对比

全部测试绑定同一个 BOSS 岗位「亚马逊运营 / 珠海 / 5–8K」，逐次核对官方面板保存值；只读取列表，没有新建任务、入队候选人、查看简历或发送消息。原条件为学历本科/硕士，院校双一流/211/985，专业电子商务类，关键词店铺运营/速卖通。没有额外的隐藏条件处于启用状态。

| --- | ---: | ---: |
| 原条件（开始时） | 1 | 15 |
| 只去掉关键词，其他保持 | 13 | 15 |

这些是当次已加载列表的数量，不是 BOSS 全库人数。原条件的交集很小；动态推荐先后出现 1 和 0 位，不应宣称整个 BOSS 库中无人符合。此次没有修改岗位规则，结束后已验证原条件恢复成功。

## 改动

- 成功响应在含有完整分页元数据时兼容省略/空的 `geekList`，再核对页面已结束加载、真实空列表或原生推荐分隔线。HTTP/业务失败、岗位错误、无分页元数据的不完整响应继续报错。
- 首批候选人 ID 必须与渲染结果的对应前缀相符，允许 BOSS 自动追加后续页；保留岗位绑定。
- 每次采集按原生分隔线排除条件外补充推荐，包括相同筛选条件已应用、不产生新请求的路径。保留分隔线前符合条件的候选人，忽略非候选人广告行。
- 采集为 0 且任务已完成时显示完成进度、0 位候选人与检查 BOSS 列表/调整官方筛选后新建任务的提示。
- 保留两个旧失败任务的历史记录，不自动重启 100 人或本次 20 人任务。
